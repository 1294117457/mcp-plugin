#### 1. Node = 内聚的工作单元

一个 Node 应该对应一个明确的业务职责，内部可能需要多步骤：

- 简单 Node：单次 LLM 调用即可完成（用 `direct` 模式）
  - 例：文本翻译、情感分析、JSON 格式化
- 复杂 Node：需要多轮 tool use 和推理（用 `subagent` 模式）
  - 例：代码审查（read + grep + 分析）、数据清洗（read + transform + write）
- 多阶段 Node：需要不同 LLM 处理不同阶段（用 `pipeline` 模式）
  - 例：修改业务代码（fast 查找 → powerful 生成方案 → standard 执行）

关键原则：Node 对外是"黑盒"，Workflow 不应该关心 Node 内部怎么实现的（是调用一次 LLM 还是十次，是用什么 tools）。

#### 2. Workflow = Node 间的依赖关系

Workflow 只管理：

- 哪些 Node 参与
- 执行顺序（chain / parallel / conditional）
- Node 间的数据传递
- 全局状态（如分支条件、HITL 暂停点）

interface WorkflowConfig {

  nodes: string[]                    *// 引用已定义的 Node*

  edges: WorkflowEdge[]              *// Node 间连线*

  topology: 'chain' | 'dag' | 'loop'

  

  *// Workflow 不关心 Node 内部实现*

}

#### 3. Task 不作为一等公民

Task 是 Node 内部的实现细节，不暴露给 Workflow：

- `direct` 模式：没有 Task 概念（单次调用）
- `subagent` 模式：Task 是 agent 自主决策的 tool call（不需手动定义）
- `pipeline` 模式：Task 对应 stage，但从外部看还是一个 Node



## 总结：推荐的设计原则

### 1. Node 颗粒度

- Node = 一个内聚的业务职责
- "修改业务代码"应该是一个 Node（用 pipeline 模式包含多阶段）
- 不要拆成 6 个 Node（过细）

### 2. Task 不作为配置

- Task 是 Node 的实现细节（subagent 的 tool call，或 pipeline 的 stage）
- Workflow 不感知 Task

### 3. State 管理

- Workflow State：Node 间共享，用于数据传递和协作
- Node State：内部私有，外部不可见
- Task 不直接读写 State（通过 Node 层统一管理）

### 4. Tool 分层

builtin tools  ──┐

MCP tools      ──┤

skill tools    ──┼──→ 注册到 Tool Registry

Node tools     ──┤      ↓

Workflow tools ──┘   被 Node/Workflow 引用

### 5. LLM 配置

- 简单 Node：配置一个 LLM
- 复杂 Node（pipeline）：每个 stage 配置不同 LLM
- 不在 Task 级别配置 LLM（过细）

这样设计的好处：

- ✅ Workflow 简洁（高层编排）
- ✅ Node 灵活（内部可简可繁）
- ✅ 状态管理清晰（两层隔离）
- ✅ 扩展性强（新增 execution mode 不影响 Workflow）
