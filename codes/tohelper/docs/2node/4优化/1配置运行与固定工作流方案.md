# 配置、运行结果与固定工作流方案

> 适用项目：`tohelper`
>
> 文档范围：配置统一、运行结果协议、固定 Pipeline、显式触发
>
> 文档状态：方案设计，暂不修改代码
>
> 更新时间：2026-08-31

## 1. 背景与目标

当前项目已经实现了 Task、Node 和 MCP Tool 的基本执行链路，但系统同时存在几套历史设计，导致配置加载、任务引用、触发方式和失败处理的行为不稳定。

本方案解决以下问题：

1. 统一 Task、Node 的配置模型和配置文件入口。
2. 让 Task 和 Node 的执行结果具备稳定、可判断、可追踪的结构。
3. 让 Pipeline 成为真正的固定工作流，按配置顺序执行，不依赖 LLM 决定是否执行某个 Task。
4. 支持用户明确指定 Node 时直接执行，以及通过 UI 按钮直接运行 Node。
5. 保留 Agent 自动选择 Node 的能力，但将它作为可选入口，而不是唯一入口。
6. 为后续 SQLite、运行历史和 Loop 调度留下清晰的接口边界。

本阶段不处理 SQLite 的落地，也不重构 Loop 的动态调度逻辑。SQLite 和 Loop 方案见《2 SQLite 与 Loop 动态编排方案》。

## 2. 当前实现审计

### 2.1 配置文件存在版本和路径冲突

当前 Host 配置读取逻辑使用：

```text
DATA_DIR/config.json
```

并且只接受 version 2，结构要求是：

```json
{
  "version": 2,
  "tasks": {},
  "nodes": {},
  "equipped": []
}
```

项目当前数据目录中可见的 Node 配置却是：

```text
DATA_DIR/node-config.json
```

该文件是 version 1，Task 直接嵌套在 Node 内部。当前执行器使用 Task ID 从 `config.tasks` 查找 Task，因此不能解析这种旧结构。

此外，工具模块的 LLM 查询逻辑也直接读取 `config.json`。如果配置入口不统一，UI 写入的配置、Host 读取的配置和 LLM 列表查询的配置可能不是同一份数据。

### 2.2 Task 的工具错误会被转换成普通文本

当前 Task 执行器捕获 Tool 异常后返回 `[Tool error] ...` 文本。上层 Pipeline 只要没有收到异常，就可能将该 Task 记录为成功，并把错误文本继续传给下一个 Task。

这会造成两个问题：

- 业务层无法区分“Tool 正常返回了一段错误描述”和“Tool 执行失败”。
- Pipeline 无法按照必需任务、可选任务和重试策略处理失败。

### 2.3 Pipeline 只传递字符串

当前 Pipeline 将原始输入提取为字符串，前一个 Task 的输出作为下一个 Task 的唯一输入。它可以支持简单的线性链，但不能表达以下常见需求：

- 后续 Task 需要访问原始用户输入。
- 汇总 Task 需要访问多个前置 Task 的结果。
- 某个 Task 失败但其他 Task 仍然可以继续。
- Task 需要明确指定输入来源，而不是依赖隐式的上一步字符串。

### 2.4 Agent 工具调用不是确定性触发

Node 装配后会注册成 Agent Tool。用户消息是否触发 Node，仍由 Agent LLM 根据 Node 名称、描述和当前上下文决定。

因此“调用 nodea”并不等于系统一定执行 nodea。用户的意图描述和 Node description 不匹配时，模型可能认为 Node 不适用。

这属于入口层的意图判断问题，不应由 Pipeline 执行器解决。

### 2.5 Node 更新后的运行时配置可能仍然是旧版本

当前 Node 更新接口在 Node 已装配时返回警告，提示需要重新装配才能应用修改。这个行为可以暂时保留，但明确运行态版本后，应该进一步支持：

- 保存时自动重新注册；或
- UI 明确显示“已装配版本”和“配置存在未应用修改”；或
- 运行请求按 Node ID 从最新存储重新读取配置。

本方案优先要求执行器每次运行使用最新的内存配置对象，并在后续 SQLite 阶段引入配置版本号。

## 3. 目标架构

### 3.1 分层职责

```text
Agent 对话层
  ├── Agent 自主选择入口：由 LLM 决定是否调用 Node Tool
  ├── 显式命令入口：识别 Node 名称后直接执行
  └── UI 运行入口：点击按钮后直接执行
          |
          v
Node Runtime
  ├── 读取 Node 定义
  ├── 创建 WorkflowContext
  ├── 按 mode 执行 Pipeline 或 Loop
  ├── 记录每个 Task 的状态
  └── 返回结构化 WorkflowResult
          |
          v
Task Runtime
  ├── 读取 Task 定义
  ├── 根据输入映射形成 Task 输入
  ├── 调用允许的 Tool 或 LLM
  ├── 标准化 Task 输出
  └── 返回 TaskResult
          |
          v
Tool Registry
  ├── 内置 Tool
  ├── MCP Tool
  └── Skill Tool
```

### 3.2 固定工作流与自然语言决策分离

Node 应该分为两类行为：

- **固定执行**：Node 配置中的步骤就是执行计划，适用于 Pipeline 和 UI/命令触发。
- **动态执行**：由 Loop 编排器决定下一步，适用于需要动态规划的场景。

固定执行时，LLM 只能负责 Task 内部的参数理解、Tool 调用和结果整理，不能决定 Node 是否跳过配置中的 Task。

## 4. 配置统一方案

### 4.1 规范配置模型

本阶段沿用当前代码已经采用的 version 2 分离模型，并补充运行和触发字段：

```ts
interface ConfigFile {
  version: 2
  tasks: Record<string, TaskConfig>
  nodes: Record<string, NodeConfig>
  equipped: string[]
}

interface TaskConfig {
  id: string
  name: string
  description: string
  taskPrompt: string
  llm: LLMSlot
  tools: string[]
  inputSchema: Record<string, unknown>
  outputSchema: Record<string, unknown>
  createdAt: string
  updatedAt?: string
}

type NodeMode = 'pipeline' | 'loop'
type TriggerMode = 'agent' | 'explicit' | 'both'
type FailurePolicy = 'fail_fast' | 'continue' | 'retry_then_continue'

interface NodeConfig {
  id: string
  name: string
  description: string
  mode: NodeMode
  nodePrompt: string
  llm: LLMSlot
  tasks: string[]
  inputSchema: Record<string, unknown>
  outputSchema: Record<string, unknown>
  triggerMode: TriggerMode
  failurePolicy: FailurePolicy
  createdAt: string
  updatedAt?: string
}
```

`triggerMode` 和 `failurePolicy` 可以在第一版先提供默认值，以降低迁移成本：

```text
triggerMode = both
failurePolicy = fail_fast
```

### 4.2 统一文件入口

短期仍然使用 JSON 时，建议只保留一个业务配置文件：

```text
DATA_DIR/config.json
```

该文件同时保存：

- `tasks`
- `nodes`
- `equipped`
- 未来的迁移版本信息

MCP Server 配置继续保留在：

```text
DATA_DIR/tool-config.json
```

MCP 配置和 Task/Node 定义职责不同，不建议在本阶段强行合并为一个 JSON 文件。

### 4.3 version 1 到 version 2 迁移

迁移必须是显式、幂等和可回滚的。启动时按以下顺序处理：

1. 如果 `config.json` 存在且 version 为 2，直接加载。
2. 如果 `config.json` 不存在，检查旧的 `node-config.json`。
3. 如果发现 version 1，先写入备份：

```text
node-config.json.backup-<timestamp>
```

4. 将每个 Node 内嵌的 Task 提取到顶层 `tasks`。
5. 将 Node 的 `tasks` 从 Task 对象数组转换为 Task ID 数组。
6. 将旧 Node 的 `tools` 字段按实际使用情况迁移到对应 Task 的 `tools`，无法确定归属的工具进入迁移警告，不自动猜测。
7. 补齐 `inputSchema`、`outputSchema`、`createdAt`、`triggerMode` 和 `failurePolicy`。
8. 以临时文件写入 `config.json`，成功后原子重命名。
9. 迁移完成后旧文件只读保留，不直接删除。

迁移结果应包含统计信息：

```json
{
  "sourceVersion": 1,
  "targetVersion": 2,
  "nodesMigrated": 1,
  "tasksMigrated": 1,
  "warnings": []
}
```

### 4.4 配置一致性校验

加载配置后必须执行校验：

- Task ID 唯一。
- Node ID 唯一。
- Task 和 Node 名称不能与其他可注册 Tool 冲突。
- Node 引用的 Task 必须存在。
- Node 至少包含一个 Task。
- Task 引用的 Tool 必须存在，或者被标记为延迟解析。
- `equipped` 中的 ID 必须指向现有 Task 或 Node。
- 不能让 Node 循环引用自身，因为当前 Node 只允许引用 Task。

校验失败时应保留可用配置，并将无效对象标记为 disabled，而不是静默将整个配置清空。

## 5. 统一执行结果协议

### 5.1 TaskResult

Task 执行器内部不再只返回字符串，而是返回：

```ts
type ExecutionStatus =
  | 'success'
  | 'failed'
  | 'timeout'
  | 'cancelled'
  | 'skipped'

interface ExecutionError {
  code: string
  message: string
  retryable?: boolean
  cause?: string
}

interface TaskResult {
  taskId: string
  taskName: string
  status: ExecutionStatus
  input?: unknown
  output?: unknown
  error?: ExecutionError
  attempt: number
  durationMs: number
  startedAt: string
  finishedAt: string
}
```

Task 的 Tool 异常应该转换成 `TaskResult.status = failed`，而不是普通成功文本。对外显示时可以将它渲染成文字，但内部状态必须保留。

### 5.2 WorkflowResult

Node 执行器统一返回：

```ts
interface WorkflowResult {
  ok: boolean
  status:
    | 'success'
    | 'partial_failure'
    | 'failed'
    | 'timeout'
    | 'cancelled'
  runId: string
  nodeId: string
  nodeName: string
  input?: unknown
  output?: unknown
  error?: ExecutionError
  steps: TaskResult[]
  startedAt: string
  finishedAt: string
}
```

状态含义：

- `success`：所有必需步骤成功，最终输出可用。
- `partial_failure`：至少一个非必需步骤失败，但仍产生可用输出。
- `failed`：必需步骤失败，或者汇总步骤失败。
- `timeout`：工作流或某个不可继续的步骤超时。
- `cancelled`：用户或系统主动取消。

### 5.3 Tool 返回格式

Node 作为 DSH Tool 时，可以继续兼容当前的：

```json
{
  "result": "用户可读文本"
}
```

但建议内部 Tool 返回完整对象：

```json
{
  "ok": true,
  "status": "success",
  "runId": "run-xxx",
  "output": "用户可读文本",
  "steps": []
}
```

`render` 函数只负责将 `WorkflowResult` 渲染为文本，不能在 render 阶段重新判断成功或失败。

### 5.4 对用户的失败提示

用户界面不应直接显示内部堆栈。建议使用以下结构：

```text
工作流未完整完成。

已完成：
- 查询麦当劳优惠券

失败：
- 查询瑞幸门店：MCP 服务超时

当前结果只包含已成功步骤的数据。
```

日志中保留详细错误、调用参数摘要和重试信息；返回给 Agent 的错误信息应简洁并可继续推理。

## 6. 固定 Pipeline 方案

### 6.1 基本语义

Pipeline 的执行顺序完全由 Node 的 Task 列表决定：

```text
原始输入
  -> Task 1
  -> Task 2
  -> Task 3
  -> Node 汇总
  -> 最终输出
```

每个 Task 都必须执行一次，除非：

- 前置必需步骤失败并使用 `fail_fast`；或
- 当前步骤被失败策略标记为 skipped；或
- 工作流被取消或超时。

Node LLM 的职责只有：

- 汇总 Task 结果。
- 按 `nodePrompt` 生成最终用户可读输出。

Node LLM 不负责选择 Pipeline 中的 Task。

### 6.2 WorkflowContext

建议执行期间维护结构化上下文：

```ts
interface WorkflowContext {
  runId: string
  nodeId: string
  originalInput: unknown
  currentInput: unknown
  taskOutputs: Record<string, unknown>
  taskResults: Record<string, TaskResult>
  variables: Record<string, unknown>
}
```

短期可以继续使用 `tasks: string[]` 表示串行顺序，同时让每个 Task 默认接收 `currentInput`。后续需要跨步骤取值时，再增加 `NodeStep` 和输入映射。

### 6.3 输入映射

为避免所有数据都被压缩成字符串，建议为 Task 增加可选输入映射：

```ts
type InputMapping =
  | { type: 'original' }
  | { type: 'previous' }
  | { type: 'task_output'; taskId: string }
  | { type: 'template'; template: string }
  | { type: 'object'; fields: Record<string, InputMapping> }
```

默认行为：

```text
第一个 Task -> originalInput
后续 Task   -> previous Task 的 output
```

映射失败时应产生明确的 `INPUT_MAPPING_ERROR`，不能悄悄传递空对象。

### 6.4 多任务并行的预留

当前 Pipeline 先实现串行，保证语义稳定。为了支持“查询多个独立来源后统一汇总”，建议后续把 `tasks: string[]` 扩展为步骤定义：

```ts
interface NodeStep {
  id: string
  taskId: string
  dependsOn: string[]
  inputMapping?: InputMapping
  required: boolean
  retryCount: number
  timeoutMs: number
}
```

当多个步骤的 `dependsOn` 相同且没有数据竞争时，可以并行执行：

```text
                 -> Task A -
原始输入 -> 分支执行             -> 汇总 Task
                 -> Task B -
```

并行执行必须使用 `Promise.allSettled` 或等价机制收集每个步骤的成功和失败，不能因为一个 Promise reject 就丢失其他步骤的结果。

### 6.5 失败策略

#### fail_fast

适合有严格前置依赖的链路：

```text
读取文件 -> 分析文件 -> 生成报告
```

读取失败后，后续步骤全部标记为 `skipped`。

#### continue

适合多个独立查询：

```text
查询商家 A
查询商家 B
查询商家 C
汇总
```

非必需步骤失败时继续执行，最终状态为 `partial_failure`。

#### retry_then_continue

先根据 Task 配置重试，超过次数后：

- 如果 Task 为 required，工作流失败。
- 如果 Task 非 required，记录失败并继续。

每次重试都应增加独立的 attempt 记录，避免覆盖第一次失败的原因。

### 6.6 汇总失败

如果所有业务 Task 成功，但 Node 汇总 LLM 失败，应返回：

- `status = failed`，如果汇总是必需的；或
- `status = partial_failure`，并将原始 Task 结果作为 fallback output。

不能返回空字符串，也不能让用户误以为所有工作流已经完成。

## 7. 确定性触发方案

### 7.1 TriggerMode

建议 Node 支持：

```ts
type TriggerMode = 'agent' | 'explicit' | 'both'
```

行为如下：

- `agent`：只通过 Agent Tool 自动选择触发。
- `explicit`：只允许命令、API 或 UI 按钮触发。
- `both`：两种入口都可用。

对固定业务工作流建议默认使用 `both`；对于有副作用的工作流，例如写文件、下单、发送消息，建议默认使用 `explicit`。

### 7.2 Agent Tool 描述

保留 Node Tool 注册能力，但在 description 中增加明确规则：

```text
这是一个固定工作流工具。
当用户明确提到 Node 名称、要求运行该 Node 或要求调用该工作流时，必须调用此工具。
不要因为用户输入与描述文本不完全一致而跳过调用。
```

这只能改善 Agent 自主触发的准确率，不能作为确定性保证。

### 7.3 显式命令

建议增加稳定的命令格式：

```text
/node <node-name> <input>
```

示例：

```text
/node coupon_summary 查询今天可用的优惠券
```

解析规则：

1. 去除命令前缀和首尾空白。
2. 按 Node 的 name 和 aliases 精确匹配。
3. 找不到 Node 时返回可用名称提示，不交给 Agent 猜测。
4. 找到后直接调用 Node Executor。
5. 返回 `runId` 和工作流结果。

Node 可选增加：

```ts
aliases: string[]
```

aliases 只能用于显式匹配，不能替代权限检查或执行校验。

### 7.4 UI 运行按钮

Node 卡片和 Node Inspector 增加“运行”操作。点击后：

1. 打开输入面板，接收符合 `inputSchema` 的输入。
2. 调用：

```text
POST /api/tohelper/node/run
```

请求示例：

```json
{
  "nodeId": "node-xxx",
  "input": {
    "input": "查询今天的优惠券"
  }
}
```

3. Host 创建 `runId`。
4. 立即返回运行已接受或直接返回短任务结果。
5. 对耗时工作流通过查询接口获取状态：

```text
GET /api/tohelper/node/runs/<runId>
```

第一版可以同步等待已有的 120 秒超时限制；后续再改成异步运行。

### 7.5 API 权限和来源

显式 API 运行必须校验：

- Node 是否存在。
- Node 是否允许 explicit 触发。
- 输入是否符合 inputSchema。
- 当前是否有有效 Agent 和 Tool 上下文。
- 是否已有相同 Node 的并发运行限制。

UI、命令和 Agent Tool 最终都应调用同一个 `NodeRuntime.run()`，不能分别复制 Pipeline 逻辑。

## 8. API 变更建议

### 8.1 Node 运行

```text
POST /api/tohelper/node/run
```

请求：

```json
{
  "nodeId": "node-xxx",
  "input": {
    "input": "用户输入"
  }
}
```

响应：

```json
{
  "ok": true,
  "runId": "run-xxx",
  "status": "success",
  "result": {
    "ok": true,
    "status": "success",
    "output": "最终结果",
    "steps": []
  }
}
```

### 8.2 运行状态

```text
GET /api/tohelper/node/runs/<runId>
```

响应直接返回 `WorkflowResult` 或其持久化查询结果。

### 8.3 配置校验

```text
GET /api/tohelper/config/validate
```

用于 UI 显示：

- 引用缺失。
- Tool 不存在。
- Schema 不合法。
- 名称冲突。
- 迁移警告。

### 8.4 API 命名兼容

当前已有 `/api/tohelper/node/list`、`create`、`update` 等接口，本阶段不必一次性改为 REST 风格。建议保留现有接口，新增 `/run` 和 `/runs/<runId>`，等 SQLite 迁移时再统一 API 版本。

## 9. 实施顺序

### 阶段 A：修复配置入口

1. 统一使用 `config.json`。
2. 增加 version 1 到 version 2 迁移。
3. 将旧 Node 内嵌 Task 拆分到顶层。
4. 修复 LLM 列表读取路径。
5. 添加加载后的配置校验。

### 阶段 B：统一执行结果

1. 增加 `TaskResult` 和 `WorkflowResult`。
2. 修改 Tool 错误处理，让失败状态向上层传播。
3. 给每个步骤记录开始时间、结束时间、attempt 和 error code。
4. 让 Tool render 负责格式化，不负责改变状态。

### 阶段 C：固定 Pipeline

1. 保留当前串行执行主流程。
2. 引入 `WorkflowContext`。
3. 区分 original input、current input 和 task outputs。
4. 增加 failure policy。
5. 增加重试、超时和 skipped 状态。
6. 让汇总阶段只读取结构化步骤结果。

### 阶段 D：确定性入口

1. 增加 `triggerMode`。
2. 增加 Node 显式运行 API。
3. 增加 UI 运行按钮和输入表单。
4. 增加 `/node name input` 命令解析。
5. 让三个入口复用同一个 Node Runtime。

## 10. 测试计划

### 配置迁移

- version 2 配置正常加载。
- version 1 配置可以生成备份并迁移。
- 重复执行迁移不会重复创建 Task。
- 缺少字段时产生警告而不是静默清空。
- Node 引用缺失的 Task 时可被检测。

### Task 执行

- 无 Tool 的 Task 能直接调用 LLM。
- Tool 参数提取成功时正常调用。
- 参数提取失败时返回 `PARAMETER_EXTRACTION_ERROR`，不使用空参数盲目调用。
- Tool 抛错后 Task 状态为 failed。
- Tool 超时后 Task 状态为 timeout。

### Pipeline

- 多个 Task 按顺序执行。
- 第二个 Task 能收到第一个 Task 的输出。
- 最终汇总能收到所有 Task 的结构化结果。
- fail_fast 会跳过后续步骤。
- continue 会返回部分成功结果。
- retry_then_continue 会记录每次 attempt。
- 汇总 LLM 失败时返回明确状态和 fallback 数据。

### 触发

- Agent 模式仍能注册为 Tool。
- explicit 模式不依赖 Agent LLM 判断。
- `/node name input` 能精确匹配 Node。
- UI 按钮使用 inputSchema 生成输入并返回 runId。
- 三个入口执行结果一致。

## 11. 暂不处理的问题

以下内容不属于本阶段：

- SQLite 数据库和数据库迁移。
- Loop 的动态任务决策协议。
- DAG 和并行步骤的完整 UI 编辑器。
- 运行历史的长期持久化。
- 分布式队列和跨进程执行。
- 复杂权限系统。

## 12. 最终结论

本阶段的核心不是继续增强 Node description，而是建立清晰的执行边界：

- Agent 自主选择只负责“是否调用”。
- 显式命令和 UI 按钮负责“确定调用”。
- Node Pipeline 负责“按固定配置执行”。
- Task 负责“完成一个业务步骤”。
- `WorkflowResult` 负责“准确表达成功、失败和部分成功”。

完成本阶段后，用户说“调用 nodea”或点击 Node 的运行按钮时，可以进入确定性的 Node Runtime；只有普通自然语言场景才继续依赖 Agent 的意图判断。
