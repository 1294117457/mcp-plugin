# 插件运行使用

> 本篇面向**使用者**视角：插件已经装好（前面 `2-插件开发步骤.md` 走完），你现在开 dsh，要怎么用、要怎么排查问题。
> 以 `my-dsh-mcp-settings` 为例，但内容是通用的——所有 dsh 外部插件都按这套流程用。

---

## 1. 日常使用流程

### 1.1 启动 dsh

```bash
# 项目根目录是 deepseek-harness
cd /home/dustp/codes/deepseek-harness

# 前台启动（看日志）
node apps/cli/lib/bin.js web
# or: pnpm dsh web
# or: ./bin/darwin-arm64 dsh web  （二进制名随平台）
# 期望输出:  dsh web: http://127.0.0.1:3080
```

> 端口可能跟 `--profile`、configuration 有关。**首行日志**会打 URL，直接打开。

### 1.2 打开设置

1. 浏览器开 URL（默认 `http://127.0.0.1:3080`）
2. 进 **设置** 弹窗（一般是右上角齿轮）
3. 左侧列表应该能看 **新插件注册的 tab**（MCP 服务是 order 20，介于 General(0)、Models(10) 之后）

> ⚠ 如果看不到 tab，按第 5 节 "找不到 tab" 排查。

### 1.3 正常使用（以 MCP 服务为例）

- **添加 server**：点 "添加 MCP server"
  - **手动表单**：填名称、连接方式 (stdio / streamable-http)、命令行 (stdio) 或 URL (http)
  - **从 JSON 导入**：粘贴 `Claude/Cursor/dsh patch` 三种格式的 JSON，点 "解析"，字段自动填入
- **保存**：点 "保存"
  - **预期**：表单折叠 + 列表增加一行 + 2 秒内右侧出现 **测试连接** + **展开工具 (N)** 按钮
  - **非预期**：见第 5 节 "保存没反应"

- **测连接**：点 "测试连接"
  - **预期**：红绿提示框
  - **绿色**：`连接成功 · <server>@<version> · <ms>ms` + `<N>个工具` + 前 10 个 tool 预览
  - **红色**：`连接失败 <code> (<stage>) · <ms>ms` + 错误 message

- **展开工具**：点 "展开工具 (N)"
  - **预期**：下面展开 tool 列表（每个 tool 的名字 + description）

- **删除**：点 "删除"
  - **预期**：浏览器弹 `confirm` 提示；点 OK 后行消失；2 秒内工具列表里消失

### 1.4 用户体验小提示（针对 MCP 这种 HMR 类型的插件）

- "保存" 后**不要**手动刷新浏览器——dsh 自己会在 2 秒内通过 SSE 通知前端（即使前端没主动 listen，浏览器自动 reload 也是另一条路）。
- "保存后" + "看到工具" 不是同一瞬间：cordis Loader 触发 patch diff → 启动新 mcp-client 实例 → 跑 MCP initialize → register tool → SSE 推工具变化 → UI 刷新。**总延迟** 100ms 到 2 秒不等，看 MCP server 启动速度。

## 2. 常用故障排查

### 2.0 一句话心法：**重启是最后手段，不是第一手段**

dsh 90% 的"插件装好但没反应"问题都跟 HMR / cache / 配置路由有关，不在 host / client 代码本身。**先重启浏览器**（硬刷 `Ctrl+Shift+R`），**再开 DevTools**看 Console。

### 2.1 找不到 tab

**症状**：打开设置，看不到 "MCP 服务" 这一行。

按下列顺序排查：

1. **DevTools → Network**，搜索 `client.js`
   - 应该看到 `GET /plugins/my-dsh-mcp-settings/client.js` 200
   - 如果不存在 → client bundle 没装到 profile 里，或 `pkg.dsh.client` 配错
2. **Console**：调 `fetch('/api/mcp/status').then(r => r.json()).then(console.log)`
   - 200 + `{ok:true, value:[...]}` → host 端 OK，问题在 client
   - 404 → 路由没注册，或 plugin 没起来
3. **检查 patch 文件**：
   ```bash
   cat ~/.dsh/profiles/<active-profile>/package.json | grep mcp
   # 应看到 "my-dsh-mcp-settings" 在 dsh.profile.bundles 里

   ls ~/.dsh/profiles/<active-profile>/node_modules/my-dsh-mcp-settings/lib/client.js
   # 应存在

   # 看 host 端是否 active
   curl http://127.0.0.1:3080/api/mcp/status
   ```
4. **看 CLI 日志**：`dsh web` 的 stdout / stderr 里搜 `my-dsh-mcp-settings` 或 `WARN`、`ERROR`。Loader 报"X has no dsh.bundle.patch"通常是 install 没装好。
5. **HMR 负向缓存**：`@deepseek-ai/dsh-client-modules` 对 "不是 client 包" 是 **永久缓存**。如果中途改了 `package.json` 的 `dsh.client`，得**重启 dsh**。
6. **端口问题**：浏览器可能开了旧的 localhost:3080 缓存。打开 DevTools → Network → "Disable cache"。

### 2.2 看到 tab 但是空白

**症状**：tab 有，里面的内容是空 / 一直 loading。

- DevTools → Console 抓 `McpStore` 报错。
- 调 `fetch('/api/mcp/status')`：
  - 若 404 → host 端路由没注册（多半 plugin 没生效，或 cordis-fiber 没 active）。
  - 若 200 但 `{ok:false}` → 看 `error.code/message`，大概率是 patch 文件读权限问题。
- 看 `~/.dsh/profiles/<active>/cordis.patch.yml` 是否真的存在。

### 2.3 保存无反应

**症状**：点 "保存" 按钮后，按钮没有 disable、表单不折叠、列表不变。

按下面这个图排查：

```
按"保存"
   │
   │ 按钮 disabled? ─→ 是 → buggy 提交函数卡死 → 进一步看 console / network
   │           │
   │           否 → 表单 onSubmit 是不是真的跑了 → 验证 onClick handler
   │
   │ onSubmit 跑了但 fetch 没发出 → 客户端 fetch 路径问题
   │           │
   │           否 → fetch 发出但 response 报错 → host 端路由问题
   │                       │
   │                       └─→ 确认 /api/mcp/add 是否注册（devtools network 200/400/500）
```

具体排查清单：

1. **DevTools → Network**：
   - 看有没有 `POST /api/mcp/add` 请求
   - 没有 → onSubmit 没触发，**多半是表单按钮真在 disabled**（填了不合规字段）。看按钮的 `disabled` 属性是否 true。
   - 有 → 点开看 response body：
     - 200 + `{ok:true,value:true}` → 后端 OK，问题在 store 的 post-success refresh
     - 400 → 后端校验失败，看返回 `error.message`
     - 500 → 后端 panic，看 dsh 控制台日志
2. **按钮 disabled** 但你没填字段：检查表单字段（`serverName`、`command` / `url` 是否非空）。
3. **都正常但 UI 没变**：99% 是浏览器缓存——`Ctrl+Shift+R` 硬刷。dsh 浏览器不会主动 invalidate `<script>`。
4. **HMR 重新触发但 fiber 没起来**：80% 是 patch 文件没原子写。看 `~/.dsh/profiles/<profile>/cordis.patch.yml` 的 inode 是不是很新。
5. **dsh CLI 控制台的报错**：找 `WARN` / `ERROR` 行，包含 `my-dsh-mcp-settings` 字样。

### 2.4 测试连接没反应

**症状**：点 "测试连接"，从来没看到红绿提示，store 里 `testing[serverName]` 永远 true。

- DevTools → Network 看 `POST /api/mcp/test` 有没有发出。
- 如果有，看 response：
  - 200 → 看 `results[i].result.ok`
  - 5xx → host 路由 500，console 找 stack。
  - 404 → 路由没注册。
- 如果没有 → 客户端 onClick → store.testServer → fetch 的链路断。
- 永远 `testing=true`，没有后续 → `finally` 的 `delete s.testing[serverName]` 没跑（异常路径）。检查 `try`/`catch` 包的对不对。

### 2.5 工具有了但是 agent 调不动

**症状**：UI 上能看到 "展开工具 (3)"，但问 dsh agent "你有什么工具" 时它说没有 MCP 工具 / 或 `tool not found`.

分两种情况：

- **dsh agent 列表里没出现 mcp__xxx__yyy**：dsh-internal 的 agent prompt fetch 没包括 tools。fetch `/api/tools/list-all`（或类似）核对。
- **list 里有但调时 `tool not found`**：多半 `tools.register` 时 name 没拼对。规则是 `mcp__<serverName>__<rawName>`（双下划线分隔），serverName 用 `[A-Za-z0-9_-]{1,32}`，rawName 跟 MCP server 自己 list 出来的一致。

排查命令：

```ts
// browser console
fetch('/api/mcp/tools').then(r => r.json()).then(console.log)
// 期望 { ok: true, value: [{ serverName: 'xxx', name: 'yyy', description: '...' }] }
```

## 3. 性能与限制

### 3.1 超时

- `/api/mcp/test` 有 5 秒 budget，超过会落 **INIT_TIMEOUT**。这是有意为之的，避免一个卡死的 mcp server 拖死整个 host。
- 其他端点（`add` / `remove`）纯文件操作，不应该有超时；如果你看到超时，**是 patch 文件读写报错。**
- 列表加载（`/api/mcp/status` + `/api/mcp/tools`）从设计上是 250ms 内合并完成。再慢就看 Loader fiber 的 state。

### 3.2 并发上限

- 同时添加多个 server：patch 文件单写者，**串行追加**。UI 上每行 add 都是独立 fetch，理论上可以并发，但 cordis Loader 收到 update 是一次性 diff；diff 几乎瞬时完成，并发 add 是安全的。
- 同时测试多个 server：每个 `/api/mcp/test` 内部 `Promise.all` 并发，**不阻塞**各 server 的 `connect + listTools`。但每个独立测试自己保有 transport，**会同时开多个 child process 或多个 HTTP 长连接**——大量 stdio server 可能会撞到 fd 上限。

### 3.3 大小限制

- `serverName` 限 1–32 位 `[A-Za-z0-9_-]`。这是为了让 `mcp__<server>__<tool>` 这个公开工具名仍然满足 dsh 的 tool naming 规约。
- args / env 是字符串数组（args）或 KV（env），**没有条目数硬上限**——但每个 cell 是 textarea，长度过大时浏览器性能会先扛不住。

## 4. 数据如何持久化与去哪里查

### 4.1 用户配置存在哪

`~/.dsh/profiles/<active-profile>/cordis.patch.yml`：

```yaml
- insert:
    - id: mcp-<serverName>
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        transport: stdio          # 或 streamable-http
        serverName: github
        command: npx
        args:
          - -y
          - '@modelcontextprotocol/github'
        env: {}
        cwd: ''
        toolCallTimeoutMs: 60000
        failOnStartupError: false
```

是 plain YAML——你可以直接编辑。但**编辑后不主动 reload**——除非 dsh HMR 看见文件 mtime 变更才触发。`touch ~/.dsh/profiles/<profile>/cordis.patch.yml` 等价"save nothing"。

### 4.2 装好的插件在哪

`~/.dsh/profiles/<active-profile>/node_modules/<plugin-name>/`：

```
node_modules/my-dsh-mcp-settings/
├─ package.json
├─ lib/
│  ├─ index.js   lib/index.d.ts
│  ├─ webserver-routes.js
│  ├─ test-connection.js
│  ├─ patch-store.js
│  ├─ config-schema.js
│  ├─ ambient.d.ts
│  ├─ client.js  client.js.map
│  └─ client/
│     └─ index.d.ts
└─ cordis.patch.yml
```

### 4.3 列出当前 profile 安装的插件

```bash
cat ~/.dsh/profiles/<active-profile>/package.json | jq .dsh.profile.bundles
# 期望: ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "my-dsh-mcp-settings"]
```

CLI 形式：

```bash
node apps/cli/lib/bin.js plugin --profile web list
node apps/cli/lib/bin.js plugin --profile web info my-dsh-mcp-settings
```

## 5. 升级与回滚插件

### 5.1 升级

开发完新版本 → 重新打 tarball → 重新 `add`：

```bash
cd my-dsh-plugin/mcp
rm -rf lib
node_modules/.bin/tsc -p .
node_modules/.bin/tsdown
tar -czf my-dsh-mcp-settings-0.1.1.tgz package.json lib cordis.patch.yml

cd /home/dustp/codes/deepseek-harness
node apps/cli/lib/bin.js plugin --profile web add \
  "file:/home/dustp/codes/my-dsh-plugin/mcp/my-dsh-mcp-settings-0.1.1.tgz"

# 重启 host（client 是 HMR-ready，host 必须重启）
pkill -f "dsh web"
node apps/cli/lib/bin.js web
```

`add` 同一名字多次时是 **覆盖**安装；CLI 内部会解 tarball 覆盖 `node_modules/<plugin-name>/`。

### 5.2 回滚

把上一个版本号（如 0.1.0）的 tarball 重新 `add` —— dsh 会替你解 tarball 覆盖。

### 5.3 卸载

```bash
node apps/cli/lib/bin.js plugin --profile web remove my-dsh-mcp-settings
# 等价: rm -rf ~/.dsh/profiles/<profile>/node_modules/my-dsh-mcp-settings
#       编辑 ~/.dsh/profiles/<profile>/package.json 移除 bundles 里的项
#       重启 dsh
```

注意：它**不会**自动清你之前通过 UI 写到 `cordis.patch.yml` 的 mcp-client 行（这是用户数据，不是插件数据）。卸载前如果想清干净：

```bash
# 备份
cp ~/.dsh/profiles/<active>/cordis.patch.yml ~/backup.patch.yml
# 手动 vim 删
```

## 6. 升级流程和写新插件的相对工作量

| 改动范围 | 工作量 | 重启 dsh？ |
|---|---|---|
| 改文案 / 改样式 / 改 UI 行为 | 重新 `tsdown` → 重打 tarball → `add` → 浏览器硬刷 | ❌（client 半边 HMR） |
| 改 host 路由 | 重新 `tsc -p .` → 重打 tarball → `add` | ✅ |
| 改 patch 文件读写 / 改 schema | 重新 `tsc -p .` → 重打 tarball → `add` | ✅ |
| 改 `cordis.patch.yml` 里 row 模板 | 重新打 tarball → `add` | ✅ |
| 加新 peer dep / 新 npm dep | 重新打 tarball → `add`（CLI 帮你 install） | ✅ |
| 加新 tab / 新 namespace | client 改动 → `tsdown` → `add` → 硬刷 | ❌ |
| 改 `package.json#name`（**不建议**） | 几乎是全新插件 | ✅ |

## 8. 安全 / 权限

- 外部插件以 **当前 dsh 进程用户身份** 运行，可以 fork 子进程、读用户 home、写 dsh home 下的文件、读主机网络。
- **不要装来路不明的 plugin tarball**——`dsh plugin add` 没有任何签字或 SBOM 验证。一个恶意 plugin 完全可以：
  - 改 `cordis.patch.yml`，让所有 mcp server 启动时调用攻击者控制的 URL
  - 监听 `/api/<自己名字>/...`，配合 XSS 截获 dsh 用户 token
  - 替换 context 影响 dsh 主进程的 token exchange
- 源码 tarball 至少先 review `src/index.ts` + `src/client/index.ts` + `cordis.patch.yml`，确定没有：
  - `eval()` / `Function(string)`
  - 未文档化的 `fs.read*` / `fetch` 到第三方
  - `pkg.dsh.client.inject` 里出现陌生条目
- dsh 主仓库的 `peerDependencies` 范围是 ds 强制的，外部插件**不能假装自己是** dsh-internal 包。

## 9. 总结：使用者视角的一张图

```
打开 dsh → 设置 → MCP 服务 (or 其他插件 tab)
   │
   ├─ 看到一个表单 → 填 → 保存
   │
   │     保存
   │       ↓
   │  patch-store 原子写 cordis.patch.yml
   │       ↓
   │  cordis-plugin-hmr fire
   │       ↓
   │  Loader diff → 启新 mcp-client
   │       ↓
   │  mcp-client tools/register
   │       ↓
   │  SSE 推 tools 变化 → UI 看到
   │
   └─ 用 agent 调用 mcp__<server>__<tool>
              ↓
         dsh-tools 命中 → call mcp-client → MCP server
```
