# 问题 1：测试连接的结果没有渲染到 UI

> 现象：用户点 "测试连接" 按钮，浏览器没看到任何工具列表，也没有看到红/绿提示框。
> 本文先解释当前实现的实际行为，再列 3 个候选修复方向，最后给推荐方案。
> 本文档**只做分析和方案**，不修改代码；确认方案后再切到 Agent 模式落地。

---

## 1. 当前实际行为——先看代码在做什么

我们目前的实现有**两条**互不交叉的"tool 数据"通道：

| 数据通道 | 来源 | 走哪条 API | 写到 store 的字段 | UI 在哪里渲染 |
|---|---|---|---|---|
| **通道 A**：已持久化的 mcp-client 在 `ctx.tools` 注册的工具 | dsh 内部，已经"活着"的 mcp-client 实例 | `/api/mcp/tools`（host 端 `collectMcpTools`） | `state.tools[serverName]` | `McpRow.tsx:108-112` 的"展开工具 (N)"按钮 + `McpRow.tsx:117-126` 的展开列表 |
| **通道 B**：Test API 一次性新建 SDK client 拿到的 tools | 当前用户的草稿 / 已保存行的配置 | `/api/mcp/test`（host 端 `testMcpConnection`） | `state.tests[serverName].preview` | `McpRow.tsx:50-84` 的 `<TestSummary>`，或 `McpForm.tsx:38-84` 的 `<DraftTestSummary>` |

**关键事实**：Test 完以后，**通道 B** 把 10 个 preview 写到了 `state.tests[serverName].preview`，但**通道 A** 的 `state.tools[serverName]` 不会自动更新——因为 `/api/mcp/tools` 只读取 dsh 当前**真正活着**的 mcp-client 实例，没经过 Test API。

也就是说：

- Test 成功 → 绿色 "连接成功 · N 个工具 · X ms" 提示框出现，里面有 preview 的前 10 个 tool 名字 → **这部分 UI 是工作的**
- 但 `McpRow.tsx:90` `const expandable = tools.length > 0`，这里 `tools` 来自 `state.tools[entry.serverName]`（通道 A）——**这条永远是空数组**，所以 "展开工具 (N)" 按钮**永远不会出现**

这就把你的现象拆成两个：

1. **绿色提示框**本来应该出现，但你没看到 → 大概率是 Test API 实际返回了 `ok:false`，或者浏览器还在跑旧 bundle。
2. **"展开工具"按钮没出现**是**当前设计的预期行为**——只有"保存 → HMR → mcp-client 起来 → 注册到 ctx.tools" 之后，通道 A 才有数据。

---

## 2. 先排除最常见的环境问题

在改代码之前，先按这张排查表走一遍——很多"测试按钮没反应"是浏览器缓存或 host 端路由问题：

| 现象 | 检查 | 结论 |
|---|---|---|
| Network 看不到 `POST /api/mcp/test` | DevTools → Network → filter `mcp/test` | 没发请求 → `McpRow.onTest` 没绑上 / `busy` 卡死 / 浏览器是旧 bundle |
| Network 看到 404 | 看 path 拼写 | 路由没注册 → host 半边没重启（`pkill -f "dsh web" && dsh web`） |
| Network 看到 500 | 看 response body | host panic，看 dsh 终端 stack |
| Network 看到 200 + `{ok:false}` | response body | Test API 实际失败：可能是 MCP server 进程没装、URL 写错、stdio transport 的 command 路径不对 |
| Network 看到 200 + `{ok:true}` + `preview.length>0` | response body | UI 应该出现绿色框——大概率浏览器 cache 没硬刷 |
| 浏览器看起来"还是老样子" | DevTools → Network → `/plugins/my-dsh-mcp-settings/client.js` 看 mtime | 旧 bundle 还在缓存里 |

**最重要的一个测试**——浏览器 console 直接调 API：

```js
// 复制一行，替换 'YOURNAME' 为你要测的 server
fetch('/api/mcp/test', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ serverName: 'YOURNAME' })
}).then(r => r.json()).then(console.log)
```

看完整结果。如果 `result.ok === true && result.preview.length > 0`，**问题 100% 在 client 渲染层**；如果 `result.ok === false`，**问题在 MCP server 那边**（child process 没装、URL 不通之类）。

## 3. 三种修复方向

### 方案 A：把 Test 拿到的 tools 直接渲染（最小改动，不动数据模型）

**思路**：用户既然点了 Test，UI 应该立即看到"这个 server 声称它有 N 个工具"，**不等** mcp-client 持久起来。把 `state.tests[serverName].preview` 也喂给 `McpRow` 渲染。

**改动**（仅 UI 层）：

1. `McpRow.tsx`：新增 prop `testPreview?: McpTestToolSummary[]`，在按钮区下方显示 "测试发现 18 个工具 ›"，点开看 preview 列表。
2. `McpSection.tsx`：把 `state.tests[entry.serverName]?.preview` 传给每个 McpRow。
3. 视觉上**明确区分**两种来源：
   - 浅灰小字 "Test: 18 个工具"（来自一次性 SDK probe，不持久）
   - 正常字体 "展开工具 (18)"（来自已 active 的 ctx.tools，持久）

**优点**：
- 改动小（约 30 行），不动数据模型、不动 host、不动 cordis patch 文件
- 视觉上给用户"立即感知"——Test 完就能数 tool

**缺点**：
- 用户**可能误解**——"我能看到 18 个工具说明 mcp-client 起来了"？其实没；这 18 个只是 server 在测试那一刻声称的
- Test 路径返回的 `preview` 只截前 10 个；用户点开发现 "Test 只显示 10 个，怎么知道后面还有？"

**适用场景**：你想快速验证、保存前的临时反馈，但不指望这成为"权威 tool 列表"。

### 方案 B：把 Test 拿到的 tools 临时注入 `state.tools`（折中）

**思路**：Test 完以后，把 `preview` 临时塞到 `state.tools[serverName]`，让现有的"展开工具"按钮复用。但**带**一个 `__from: 'test'` 标记，UI 显示时说明"测试时声称的 N 个工具，待持久 mcp-client 起来后会被真实值替换"。

**改动**：

1. `mcp-store.ts`：在 `testServer()` 末尾，除了写 `s.tests[serverName]` 之外，再写 `s.tools[serverName] = (preview ?? []).map(p => ({ serverName, name: p.name, description: p.description ?? '' }))`。
2. `McpRow.tsx`：在按钮区右侧加一个小角标 `(来自测试，待 HMR)`。
3. `mcp-store.ts` 的 `load()` 逻辑里：load 完后用 `ctx.tools` 的真实数据**覆盖** `state.tools[serverName]`——这样 mcp-client 真正起来后，preview 数组被"真值"替换。

**优点**：
- 复用现有 UI，"展开工具 (N)" 按钮立即可见
- 后续 HMR 触发 mcp-client 真起来后，preview 自动被真值替换，不需要单独清

**缺点**：
- 混合两套数据源（"测试声称的 tool" 和 "mcp-client 实际注册的 tool"），状态语义变模糊
- 用户预期 "展开 (N)" 是事实，看到 "Test 声称 18 个工具" 但 dsh agent 实际只调用到 15 个——会比较困惑
- 如果 MCP server 跟 dsh 跑在不同机器，server 端重启加了新 tool，UI 不会自动感知

**适用场景**：你想让"展开"按钮立即出现，但能接受状态语义模糊。

### 方案 C：Test API 直接驱动 mcp-client 起来（彻底方案）

**思路**：撤销现在 Test API 的"一次性 SDK probe"实现，**直接复用 `@deepseek-ai/dsh-mcp-client`**，**让 cordis Loader 加载一条新的 mcp-client 实例**——只不过带 `testOnly: true` 配置，让它启起来 + 注册 tool 后立刻 dispose。

**改动**：

1. `test-connection.ts` 删了，改用 `ctx.loader.create({ name: '@deepseek-ai/dsh-mcp-client', config: { ...testConfig, ephemeral: true } })`。
2. 等新 fiber `state === ACTIVE` 后，调 `ctx.tools.layers.merge(...)` 把 tool 列表读出来。
3. 立即 dispose 这条 fiber。
4. UI 的 `state.tools[serverName]` 这次是真的——`/api/mcp/tools` 在 fiber dispose 后**反而会清掉**，所以走单独的 "test-time tools map"。

**优点**：
- 跟生产路径走的是同一套 mcp-client 协议，UI 看到的 tool 列表 100% 等价 dsh agent 看到的
- 自然处理了"config 写错 / spawn 失败 / handshake 失败"这些 case——mcp-client 自己有完整错误码

**缺点**：
- **大改动**：测试一个草稿 config 会在 cordis 里新建 fiber + dispose，**频繁操作可能影响 dsh 主流程**
- `@deepseek-ai/dsh-mcp-client` 没有 `ephemeral` 模式，得先 PR 一个
- 还是绕不开 "Test 完了用户没保存" → mcp-client 已经 dispose → agent 调不到这个 tool

**适用场景**：你想保证"UI 看到的 = agent 调到的"，但不介意大改 + 给上游 PR。

## 4. 推荐：方案 A + 小幅补丁

**为什么选 A**：
- **改动量最小**（~30 行 UI），不动 host、不动 data model
- 用户的核心需求是"测完能立刻看到工具"，A 直接满足
- B 的数据语义模糊是**后期 bug 源**；C 改动量 + PR 成本都太大
- A 跟"测试"语义天然对齐——"这只是临时探一下，不代表 agent 能用"

**具体落地清单**（等你点头才动）：

1. `src/client/McpSection.tsx`：McpRow 加 `testPreview` prop（`state.tests[entry.serverName]?.preview ?? []`）。
2. `src/client/McpRow.tsx`：
   - 新增 `testPreview?: McpTestToolSummary[]` prop
   - 在按钮区下方加一个**条件渲染区**：`{testPreview.length > 0 ? <details><summary>测试发现 {testPreview.length} 个工具</summary>...</details> : null}`
   - 视觉上跟"展开工具 (N)"区分（不同色 / 不同字号 / 标 "(来自测试)"）
3. `src/client/McpSection.module.css`：加 `.testPreviewSection` / `.testPreviewHeader` 类。
4. `src/client/locales.ts`：加 `testPreviewTitle: '测试发现 {count} 个工具（临时）'`。
5. 同步给 `McpForm.tsx` 的 `<DraftTestSummary>`：现在已经有 preview 渲染，**不动**，确认能正常工作。

**同时建议改的小补丁**（不增加代码量，提升 UX）：

- `<TestSummary>` 在失败时**强制显眼**——目前是 `css.testFail` 但被埋在 row 末尾。加 `role="alert"` 让屏幕阅读器立即播报；视觉上移到 row 顶部，**在徽标旁**显示失败图标。
- Test 按钮在 `testing=true` 时显示 spinner 而不是文字（已有 `aria-busy` 但视觉反馈弱）。

**验证步骤**：

1. 重新 build + pack + 重装 + 重启 dsh + **Ctrl+Shift+R 硬刷浏览器**
2. Network 看 `POST /api/mcp/test` 实际 response
3. UI 上点 Test，看到绿色框 + "测试发现 N 个工具" 折叠区
4. 点开折叠区，能看到前 10 个 tool 的 preview
5. 保存后，"展开工具 (N)" 按钮也出现——这是**真实** ctx.tools 数据，跟测试 preview 是两套

---

## 5. 不要做的事

- **不要**让 Test 路径直接调 `ctx.loader.create` 去启 mcp-client——除非你已经准备好方案 C 的工作量，否则会引入"测试后没保存但 mcp-client 真的跑了"的怪状态。
- **不要**把 `state.tests[serverName].preview` **也**塞到 `state.tools[serverName]`——这两条路径一旦合并，HMR 替换 mcp-client 时会出幽灵数据。
- **不要**改 Test API 的 host 实现 (`test-connection.ts`)——它现在的工作是 OK 的，问题在 UI 怎么用它的返回。

## 6. 验证你能不能看到 Test 结果的最快方法

如果上面方案 A 还没实施，你想现在就确认 Test API 真的返回了工具，调下面这串：

```js
// 浏览器 console
(async () => {
  const r = await fetch('/api/mcp/test', {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({
      config: {
        transport: 'streamable-http',
        serverName: 'github',
        url: 'https://api.githubcopilot.com/mcp/',
        headers: { Authorization: 'Bearer ghp_xxxx' },
        toolCallTimeoutMs: 60000,
        failOnStartupError: false
      }
    })
  })
  const j = await r.json()
  console.log(JSON.stringify(j, null, 2))
})()
```

如果 `j.value.results[0].result.ok === true && j.value.results[0].result.preview.length > 0`：

- 恭喜，host API 完全 OK，问题 100% 在 client 渲染 + 浏览器 cache
- 走 Ctrl+Shift+R，再观察 UI

如果 `j.value.results[0].result.ok === false`：

- 把 `result.error` 的 `code / message / stage` 贴出来，host 端那个 5 秒 probe 已经给了足够诊断信息
- 这不是"UI 渲染"问题，是"你的 MCP server 配置不对"问题——多半是 child process spawn 失败 / URL 不通 / Auth header 拼错

## 7. 总结一句话

> 当前 Test API 拿到的 tool 列表**只渲染在绿色提示框里**（前 10 个 preview），右侧 "展开工具 (N)" 按钮因为需要"已激活 mcp-client 在 ctx.tools 注册"才显示，**Test 不触发它**。用户看不到工具的根因多半是 **Test 实际失败（host 端 5 秒超时或连接错误）** 或 **浏览器 cache 没硬刷**。
> 推荐方案 A：在 McpRow 加一个 "测试发现 N 个工具（临时）" 的折叠区，明确区分测试 vs 持久两套 tool 来源。
